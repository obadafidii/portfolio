# Write-Ahead Logs

Every database makes a promise it cannot technically keep: *when I say the write succeeded, it succeeded.* The machine can lose power a microsecond after the acknowledgement leaves the socket, and the user still expects their data to be there when it comes back.

A write-ahead log is how that promise gets kept. The idea fits in one sentence — **record what you are about to do before you do it** — and almost everything interesting about storage engines falls out of taking that sentence seriously.

I built one for [KvShard](https://github.com/obadafidii/KvShard) and got most of it wrong the first time. This is what I wish I had read first.

---

## The problem, concretely

Say you have an in-memory map and you persist it to disk every few seconds.

```go title="store.go — the lie"
type Store struct {
    mu   sync.RWMutex
    data map[string]string
}

func (s *Store) Set(key, value string) error {
    s.mu.Lock()
    defer s.mu.Unlock()
    s.data[key] = value
    return nil // "success"
}
```

That `return nil` is a lie. The value exists in one place — volatile memory. Between two flushes you might have thousands of acknowledged writes with no on-disk representation whatsoever.

The obvious fix is to write the whole map to disk on every `Set`. That is correct and unusably slow: rewriting a 2GB file to change nine bytes. Worse, it is *not even safe* — a crash halfway through leaves a file that is neither the old state nor the new one.

The insight is that you do not need to persist the **state**. You need to persist the **change**, and changes are small, and they only ever get appended.

<WalFlow />

That ordering is the whole discipline. The log becomes durable *first*. Memory is mutated *second*. The client is told yes *last*. Get the order wrong and you have a database that acknowledges writes it cannot recover.

## Anatomy of a record

A log is a file you only append to, so the format has to answer one question on its own: where does this record end and the next begin?

<RecordLayout />

Three details in that header matter more than they look.

**The length prefix** means recovery never scans for a delimiter. Read 4 bytes, learn the size, read exactly that many. Delimiter scanning breaks the moment a payload contains the delimiter, and payloads are arbitrary bytes.

**The checksum comes first and covers everything after it.** During replay you cannot trust that the last record is complete — the process may have died mid-`write`. The CRC is the only way to distinguish a valid record from a half-written one.

**The type field** exists because a record can be larger than the space left in the current block. Rather than pad or refuse, you split it: `first`, `middle`, `middle`, `last`. This is what LevelDB and RocksDB do, and it is why their logs are block-structured rather than a flat byte stream.

Here is the encoder:

```go title="wal/record.go" showLineNumbers
package wal

import (
    "encoding/binary"
    "hash/crc32"
)

type RecordType uint8

const (
    RecordFull RecordType = iota + 1
    RecordFirst
    RecordMiddle
    RecordLast
)

const headerSize = 4 + 4 + 1 + 8 // crc + length + type + lsn

var castagnoli = crc32.MakeTable(crc32.Castagnoli)

type Record struct {
    LSN     uint64
    Type    RecordType
    Payload []byte
}

// Encode lays a record out as: crc | length | type | lsn | payload.
// The CRC covers every byte after itself.
func (r Record) Encode() []byte {
    buf := make([]byte, headerSize+len(r.Payload))

    binary.LittleEndian.PutUint32(buf[4:8], uint32(len(r.Payload)))
    buf[8] = byte(r.Type)
    binary.LittleEndian.PutUint64(buf[9:17], r.LSN)
    copy(buf[headerSize:], r.Payload)

    sum := crc32.Checksum(buf[4:], castagnoli)
    binary.LittleEndian.PutUint32(buf[0:4], sum)

    return buf
}
```

Use Castagnoli, not the default IEEE polynomial. Modern CPUs implement it in hardware via `SSE4.2`, and Go's `crc32` package picks that path automatically. On a hot write path this is the difference between the checksum being free and being your bottleneck.

The payload itself is deliberately opaque to the log. The WAL's job is framing and durability; what the bytes mean is the storage engine's problem.

```go title="wal/mutation.go"
type OpKind uint8

const (
    OpSet OpKind = iota + 1
    OpDelete
)

type Mutation struct {
    Kind  OpKind
    Key   []byte
    Value []byte
}

func (m Mutation) Marshal() []byte {
    buf := make([]byte, 0, 1+4+len(m.Key)+4+len(m.Value))
    buf = append(buf, byte(m.Kind))
    buf = binary.LittleEndian.AppendUint32(buf, uint32(len(m.Key)))
    buf = append(buf, m.Key...)
    buf = binary.LittleEndian.AppendUint32(buf, uint32(len(m.Value)))
    return append(buf, m.Value...)
}
```

## Writing, and the part everyone gets wrong

Here is a first attempt at the writer:

```go title="wal/writer.go"
type Writer struct {
    mu   sync.Mutex
    file *os.File
    buf  *bufio.Writer
    lsn  uint64
}

func (w *Writer) Append(m Mutation) (uint64, error) {
    w.mu.Lock()
    defer w.mu.Unlock()

    w.lsn++
    rec := Record{LSN: w.lsn, Type: RecordFull, Payload: m.Marshal()}

    if _, err := w.buf.Write(rec.Encode()); err != nil {
        return 0, err
    }
    return w.lsn, nil
}
```

This is fast and it is not a write-ahead log. The bytes are in a `bufio.Writer` inside your own process. A panic loses them. The kernel has never seen them.

Add a flush and it gets better, but only by one rung:

```go
if err := w.buf.Flush(); err != nil { // now the kernel has it
    return 0, err
}
```

Now your process can die and the data survives, because the kernel owns those pages and will write them out eventually. Pull the power cord and it is still gone — page cache is RAM.

<DurabilityLadder />

The only call that makes a durability promise is `fsync`:

```go title="wal/writer.go — with fsync" showLineNumbers
func (w *Writer) Append(m Mutation, sync bool) (uint64, error) {
    w.mu.Lock()
    defer w.mu.Unlock()

    w.lsn++
    rec := Record{LSN: w.lsn, Type: RecordFull, Payload: m.Marshal()}

    if _, err := w.buf.Write(rec.Encode()); err != nil {
        return 0, err
    }
    if !sync {
        return w.lsn, nil
    }
    if err := w.buf.Flush(); err != nil {
        return 0, err
    }
    // Sync blocks until the device confirms the write. This is the
    // millisecond that buys you crash safety.
    if err := w.file.Sync(); err != nil {
        return 0, err
    }
    return w.lsn, nil
}
```

Two warnings that cost me real time.

**`file.Sync()` is not free and not fast.** On a consumer NVMe drive expect somewhere in the hundreds of microseconds; on network-attached storage, several milliseconds. If you fsync per write, your write throughput is exactly `1 / fsync_latency` — a few hundred to a few thousand operations per second, no matter how fast the rest of your code is.

**Some drives lie.** Consumer SSDs with volatile write caches have historically acknowledged `FLUSH` before the data reached NAND. If you genuinely need power-loss durability, you need hardware with power-loss protection, or you accept the risk explicitly. Do not let a benchmark convince you your fsync got faster; it usually means it stopped happening.

## Group commit

If each writer must wait a full fsync, and fsync latency is fixed, the only lever left is **how many writers share one fsync**.

```go title="wal/batch.go" showLineNumbers
type commit struct {
    rec  Record
    done chan error
}

type BatchWriter struct {
    incoming chan commit
    file     *os.File
    buf      *bufio.Writer
}

func (b *BatchWriter) run() {
    pending := make([]commit, 0, 64)

    for first := range b.incoming {
        pending = append(pending[:0], first)

        // Drain whatever else is already waiting. Everyone who arrived
        // while the previous fsync was in flight rides this one.
        drain:
        for len(pending) < cap(pending) {
            select {
            case next := <-b.incoming:
                pending = append(pending, next)
            default:
                break drain
            }
        }

        var err error
        for _, c := range pending {
            if _, err = b.buf.Write(c.rec.Encode()); err != nil {
                break
            }
        }
        if err == nil {
            if err = b.buf.Flush(); err == nil {
                err = b.file.Sync() // one syscall for the whole batch
            }
        }

        for _, c := range pending {
            c.done <- err
        }
    }
}

func (b *BatchWriter) Append(rec Record) error {
    done := make(chan error, 1)
    b.incoming <- commit{rec: rec, done: done}
    return <-done
}
```

Every caller still waits a full fsync — latency is unchanged. But throughput now scales with batch size, and batch size grows naturally under load: the busier you are, the more writers pile up during each fsync, the more efficient each one becomes. The system gets *more* efficient under pressure, which is a rare and pleasant property.

## Segments and rotation

A single log file grows forever, and you cannot delete the front of a file. So you cut the log into numbered segments and delete whole ones.

```go title="wal/segment.go"
type Log struct {
    dir      string
    active   *Writer
    segment  uint64
    maxBytes int64
}

func (l *Log) rotateIfNeeded() error {
    info, err := l.active.file.Stat()
    if err != nil {
        return err
    }
    if info.Size() < l.maxBytes {
        return nil
    }
    return l.rotate()
}

func (l *Log) rotate() error {
    if err := l.active.buf.Flush(); err != nil {
        return err
    }
    if err := l.active.file.Sync(); err != nil {
        return err
    }
    if err := l.active.file.Close(); err != nil {
        return err
    }

    l.segment++
    path := filepath.Join(l.dir, fmt.Sprintf("%016d.wal", l.segment))

    f, err := os.OpenFile(path, os.O_CREATE|os.O_WRONLY|os.O_APPEND, 0o644)
    if err != nil {
        return err
    }
    l.active = &Writer{file: f, buf: bufio.NewWriterSize(f, 64<<10), lsn: l.active.lsn}

    // The new file's directory entry is not durable until the directory
    // itself is synced. Skip this and a crash can lose the whole segment.
    return syncDir(l.dir)
}

func syncDir(dir string) error {
    d, err := os.Open(dir)
    if err != nil {
        return err
    }
    defer d.Close()
    return d.Sync()
}
```

That `syncDir` call is the single most commonly omitted line in hand-rolled WAL implementations. Creating a file and fsyncing *the file* does not make the **directory entry** durable. Crash at the wrong moment and you have a perfectly synced file that the filesystem has no record of. Zero-pad the segment names too, so lexical order matches numeric order and recovery can just sort filenames.

## Recovery

Recovery is a fold over the log. Start from empty state, apply every valid record in order, stop at the first one that fails its checksum.

<CrashReplay />

```go title="wal/replay.go" showLineNumbers
func (l *Log) Replay(apply func(Mutation) error) (uint64, error) {
    segments, err := filepath.Glob(filepath.Join(l.dir, "*.wal"))
    if err != nil {
        return 0, err
    }
    sort.Strings(segments)

    var lastLSN uint64

    for _, path := range segments {
        f, err := os.Open(path)
        if err != nil {
            return lastLSN, err
        }

        r := bufio.NewReaderSize(f, 64<<10)
        header := make([]byte, headerSize)

        for {
            if _, err := io.ReadFull(r, header); err != nil {
                if errors.Is(err, io.EOF) || errors.Is(err, io.ErrUnexpectedEOF) {
                    break // clean end, or a torn header — either way, stop
                }
                f.Close()
                return lastLSN, err
            }

            want := binary.LittleEndian.Uint32(header[0:4])
            length := binary.LittleEndian.Uint32(header[4:8])
            lsn := binary.LittleEndian.Uint64(header[9:17])

            payload := make([]byte, length)
            if _, err := io.ReadFull(r, payload); err != nil {
                break // record was cut short by the crash
            }

            sum := crc32.Update(
                crc32.Checksum(header[4:], castagnoli),
                castagnoli, payload,
            )
            if sum != want {
                break // torn or corrupt: everything after this is suspect
            }

            m, err := UnmarshalMutation(payload)
            if err != nil {
                f.Close()
                return lastLSN, err
            }
            if err := apply(m); err != nil {
                f.Close()
                return lastLSN, err
            }
            lastLSN = lsn
        }
        f.Close()
    }

    return lastLSN, nil
}
```

The crucial decision is what `break` means on a checksum failure. **Stop, do not skip.** A corrupt record means you are looking at the tail the crash interrupted; records after it are either absent or untrustworthy. Skipping ahead and applying what looks valid can resurrect a mutation whose predecessor was lost, producing state that never existed at any point in time. Silent corruption is far worse than data loss you can detect.

Notice too that recovery is naturally **idempotent**: replaying `SET user:1 = "ada"` twice yields the same state. That is not an accident — it is a design constraint. If your operations were relative (`INCREMENT balance BY 50`), replaying after a partial recovery would double-count. Log the resulting value, not the delta.

## Checkpoints, so the log does not grow forever

Replay from record one is fine for a toy and unacceptable for a database that has been up for a month. A checkpoint records that everything up to some LSN is already durable in the main data structure, so recovery can start from there.

```go title="wal/checkpoint.go"
type Checkpoint struct {
    LSN      uint64 `json:"lsn"`
    Segment  uint64 `json:"segment"`
}

func WriteCheckpoint(dir string, cp Checkpoint) error {
    blob, err := json.Marshal(cp)
    if err != nil {
        return err
    }

    tmp := filepath.Join(dir, "CHECKPOINT.tmp")
    f, err := os.Create(tmp)
    if err != nil {
        return err
    }
    if _, err := f.Write(blob); err != nil {
        f.Close()
        return err
    }
    if err := f.Sync(); err != nil {
        f.Close()
        return err
    }
    if err := f.Close(); err != nil {
        return err
    }

    // Rename is atomic within a filesystem: readers see the old file or
    // the new one, never a half-written mix.
    if err := os.Rename(tmp, filepath.Join(dir, "CHECKPOINT")); err != nil {
        return err
    }
    return syncDir(dir)
}
```

Write-to-temp then rename is the standard trick for atomically replacing a file, and it works because POSIX guarantees `rename` is atomic within a filesystem. Once the checkpoint is durable, every segment whose highest LSN is below `cp.LSN` can be deleted.

Order matters here as much as anywhere else:

1. Flush the memtable to its permanent home (an SSTable, say) and fsync it.
2. Write and fsync the checkpoint.
3. *Then* delete the obsolete segments.

Delete before the checkpoint is durable and a crash in between leaves you with neither the log records nor the checkpoint that made them redundant.

## What to measure

Numbers that told me something useful, in rough order of how often they surprised me:

| metric | why it matters |
| --- | --- |
| fsync p99, not mean | the mean hides the flush stalls that cause your timeout spikes |
| batch size distribution | if it stays at 1 under load, your group commit is not grouping |
| bytes written vs bytes logged | large headroom means header overhead is dominating small writes |
| replay time per GB | this is your recovery time objective, measured rather than guessed |
| segments deleted per hour | if this is zero, checkpointing is broken and disk will fill |

The one I would insist on: **test recovery by actually killing the process.** Not `defer cleanup()`, not a unit test that calls `Replay` on a well-formed file. `SIGKILL` mid-write, then replay, then assert. Every WAL bug I have written was invisible to tests that shut down politely.

```go title="wal/recovery_test.go"
func TestRecoveryAfterKill(t *testing.T) {
    dir := t.TempDir()

    cmd := exec.Command(os.Args[0], "-test.run=TestWriterChild")
    cmd.Env = append(os.Environ(), "WAL_CHILD=1", "WAL_DIR="+dir)
    if err := cmd.Start(); err != nil {
        t.Fatal(err)
    }

    time.Sleep(200 * time.Millisecond) // let it write a while
    if err := cmd.Process.Kill(); err != nil {
        t.Fatal(err)
    }
    _ = cmd.Wait()

    log, err := Open(dir)
    if err != nil {
        t.Fatal(err)
    }

    state := map[string]string{}
    lsn, err := log.Replay(func(m Mutation) error {
        switch m.Kind {
        case OpSet:
            state[string(m.Key)] = string(m.Value)
        case OpDelete:
            delete(state, string(m.Key))
        }
        return nil
    })
    if err != nil {
        t.Fatalf("replay after kill: %v", err)
    }

    // Every record the child was told succeeded must be present.
    for i := uint64(1); i <= lsn; i++ {
        key := fmt.Sprintf("key:%d", i)
        if _, ok := state[key]; !ok {
            t.Fatalf("acknowledged write %s lost after crash", key)
        }
    }
}
```

## Where this shows up

Once the shape is familiar you start seeing it everywhere. PostgreSQL's WAL is the same idea, with segments and checkpoints under those exact names. SQLite's WAL mode replaces its older rollback journal with this. RocksDB and LevelDB pair it with a memtable, exactly as above. Kafka is arguably a write-ahead log that decided the log itself was the product. Raft's replicated log is this structure again, with the durability requirement extended across machines rather than across a power cycle.

The recurring lesson is unglamorous: **ordering is the feature.** Not the encoding, not the checksum, not even fsync in isolation. The guarantee comes from the fact that the log is durable before memory changes, and memory changes before anyone is told yes. Every serious bug I hit came from breaking that order somewhere — usually to make a benchmark look better.
